# 빨강 게이트에 실패 사유 종수 세기

## 배경

파이프라인의 빨강 게이트는 지금 "수집 1건 이상 && 통과 0건" 만 본다
(`scripts/ai-team/gate.mjs:43`). 이건 "테스트가 돌긴 한다" 는 증명이지
"테스트가 스펙을 구별한다" 는 증명이 아니다.

실제로 첫 성공 실행에서 빨강 61건이 **전부 같은 에러**였다 — 클로드가 쓴
껍데기의 throw 하나. 61건이 재어진 것처럼 보였지만 실제로 구별된 것은 0가지다.

그래서 빨강 단계에서 **서로 다른 실패 사유가 몇 가지인지** 세어 한 가지뿐이면
경고를 남긴다. **막지는 않는다** — 껍데기 throw 는 정상 패턴이므로 진행을
멈출 근거가 못 된다. 아침에 사람이 로그에서 보고 판단할 한 줄이면 된다.

## 어디에 만드나

- 판정: `scripts/ai-team/gate.mjs` 에 **순수 함수로** 추가한다.
- 배선: `scripts/ai-team/pipeline.mjs`.

## 테스트 파일은 새로 만든다 (중요)

새 테스트는 **`webapp/src/lib/ai-team/gate.failure-kinds.test.ts`** 에 쓴다.
기존 `gate.test.ts` 에 덧붙이면 안 된다.

이유: 빨강 게이트는 지정된 테스트 파일들에서 **통과가 0건**이어야 한다. 기존
`gate.test.ts` 에는 이미 통과하는 테스트가 13건 있어서, 거기에 덧붙이면
빨강 게이트가 UNEXPECTED_PASS 로 즉시 죽는다. 저장소에 이미
`reducer.actions.test.ts` / `EndingScreen.aftermath.test.tsx` 처럼 관점별로
쪼갠 선례가 있다.

기존 `gate.test.ts` 는 **한 줄도 고치지 않는다.** redGate / greenGate 의
동작과 반환값은 그대로다.

## 만들 것 1 — failureKinds(messages)

실패 메시지 목록에서 **서로 다른 사유**만 골라 돌려준다.

    export function failureKinds(messages) -> string[]

정규화 규칙 — 메시지 하나마다 순서대로 적용한다.

1. 줄바꿈 기준 **첫 줄만** 취한다. 스택 트레이스는 버린다.
2. 양끝 공백을 없앤다.
3. 첫 줄 안의 **절대 경로 토큰**을 문자열 `<경로>` 로 바꾼다. 절대 경로
   토큰이란 슬래시로 시작하고 공백이 없는 연속 문자열이다. 워크트리 경로에
   실행 시각이 박혀 있어 그대로 두면 실행마다 사유가 달라진다.
4. 결과가 빈 문자열이면 **사유로 세지 않는다**(목록에서 뺀다).

같은 사유는 한 번만 담는다. 순서는 **처음 나온 순서**를 유지한다.

경계에서 이렇게 동작해야 한다.

| 입력 | 결과 |
|---|---|
| null 또는 undefined | 빈 배열 |
| 빈 배열 | 빈 배열 |
| 빈 문자열 / 공백만 / 줄바꿈만 인 항목 | 빈 배열 |
| 배열 항목이 null, undefined, 문자열이 아닌 값 | 그 항목만 건너뛴다 |
| 같은 메시지 두 개 | 한 가지 |
| B, A, B 순서 | B, A (처음 나온 순서) |
| 첫 줄 뒤에 스택이 붙은 메시지 | 첫 줄만 |
| 앞뒤에 공백이 붙은 메시지 | 공백을 뗀 것 |
| 절대 경로만 다른 두 메시지 | 한 가지 (경로가 자리표시자로 바뀐다) |
| 상대 경로가 든 메시지 | 안 바꾼다 (슬래시로 시작하지 않는다) |
| 첫 줄에 절대 경로가 둘 | 둘 다 각각 자리표시자로 바뀐다 |

## 만들 것 2 — redDiscriminationWarning(counts, messages)

빨강이 스펙을 구별하는지에 대한 **경고 문구**. 경고할 것이 없으면 null.

    export function redDiscriminationWarning(counts, messages) -> string | null

counts 는 redGate 가 받는 것과 같은 모양(numTotalTests, numPassedTests).
판정 순서는 이렇다.

1. counts 가 null 또는 undefined 면 null. 못 읽은 것이지 판별력 문제가 아니다.
2. counts.numTotalTests 가 2 보다 작으면 null. 한 건뿐이면 사유가 한 가지인 게
   당연하다.
3. failureKinds(messages) 의 길이가 0 이면 null. **모르는 것을 경고하지 않는다.**
   (빨강 게이트와 다른 태도다. 게이트는 막는 것이라 모르면 안 통과시키지만,
   이건 경고라 모를 때 떠들면 소음만 된다.)
4. 길이가 2 이상이면 null. 구별되고 있다.
5. 길이가 정확히 1 이면 아래 문구를 돌려준다.

문구는 **정확히** 이 모양이다. 중괄호 자리에 값이 들어간다.

    빨강 {N}건이 전부 같은 사유입니다 — 테스트가 스펙을 구별하는지 아직 증명되지 않았습니다: {사유}

- {N} 은 counts.numTotalTests 값.
- {사유} 는 그 유일한 정규화 사유.
- 사유가 **200자를 넘으면** 앞 200자만 남기고 말줄임표 한 글자(U+2026)를 붙인다.
  정확히 200자면 자르지 않고 말줄임표도 붙이지 않는다.

경계에서 이렇게 동작해야 한다.

| counts | messages | 결과 |
|---|---|---|
| null | 사유 하나 | null |
| 총 2 통과 0 | null | null |
| 총 1 통과 0 | 사유 하나 | null (한 건뿐) |
| 총 0 통과 0 | 사유 하나 | null |
| 총 2 통과 0 | 빈 배열 | null (못 읽었다) |
| 총 2 통과 0 | 공백뿐인 항목들 | null (셀 사유가 없다) |
| 총 2 통과 0 | 서로 다른 사유 둘 | null (구별된다) |
| 총 61 통과 0 | 같은 메시지 61개 | 경고 문구, N 자리가 61 |
| 총 2 통과 0 | 201자짜리 사유 | 앞 200자 + 말줄임표 |
| 총 2 통과 0 | 정확히 200자짜리 사유 | 그대로, 말줄임표 없음 |

numPassedTests 는 보지 않는다. 통과 건이 있는지는 redGate 의 일이다.

## 만들 것 3 — 배선

pipeline.mjs 두 곳만 손댄다.

1. runTests 가 counts, output 에 더해 **failures** 를 돌려주게 한다.
   failures 는 실패한 assertion 들의 failureMessages 를 순서대로 이어 붙인
   **문자열 배열**이다. 지금은 detail 문자열로 뭉개져 나온다
   (`pipeline.mjs:121`). 리포터를 못 읽었으면 빈 배열.
   counts 와 output 의 기존 동작과 모양은 그대로 둔다.

2. 빨강 게이트가 통과한 직후(`pipeline.mjs:436` 부근) 경고를 계산해
   null 이 아니면 log() 로 **한 줄** 남긴다. **진행을 막지 않는다.**

배선은 최상위에서 도는 스크립트라 단위 테스트 대상이 아니다. 테스트는 위
순수 함수 둘만 덮는다.

## 하지 않을 것

- redGate 의 시그니처와 반환값을 바꾸지 않는다.
- 초록 게이트는 이번에 손대지 않는다 (사람이 아직 정하지 않았다).
- 경고 때문에 파이프라인이 멈추게 하지 않는다.
